# Alexios Web V3 — integração com Python por turnos

## Escopo

A versão V3 reutiliza `/v2/agent/poll` e `/v2/agent/state` para
presença/comandos. O Python `continuous_v3.py` usa a mesma
`ALEXIOS_AGENT_TOKEN` e a mesma `ALEXIOS_INSTANCE_ID` de antes.
O painel mantém cookie HTTP-only e `/api/v2/alexios/status`.

O servidor possui **uma memória compartilhada por instância** na coluna
`alexios_sessions.context_text`. `speakerId` é um atributo de cada evento,
não uma chave de memória. `runId` controla a execução ativa e distingue
speaker IDs efêmeros após reinicializações.

A migração `db/migrations/004_v3_events.sql` deve ser aplicada primeiro,
em preview e depois em produção, **antes** do deploy do código que consulta
as novas colunas. Não altera nem exclui dados existentes.

## Endpoints Python

Todos os cinco endpoints exigem `Authorization: Bearer <ALEXIOS_AGENT_TOKEN>`,
`instanceId` e `runId` válidos, e uma lease V2 ativa (poll recente):

| Endpoint | Entrada | Resposta |
|---|---|---|
| POST `/v3/agent/sync` | Identidade da execução | `{ "nextSequence": 1 }` |
| POST `/v3/agent/activity` | `state: "speech_started"`, `activityEpoch` | `{ "accepted": true }` |
| POST `/v3/agent/chunk` | Evento com `sequence`, `eventId`, `turnId`, `speakerId`, `transcript`, timestamps e `activityEpoch` | `{ "accepted": true }` |
| POST `/v3/agent/turn` | Idem, mas turno concluído pelo Smart Turn | `{ "accepted": true }` |
| POST `/v3/agent/floor` | `sequence`, `eventId`, `afterSequence`, `silenceMs`, `activityEpoch` | `{ "accepted": true }` |

`202 Accepted` significa persistido e publicado na fila, **não**
resposta pronta. Todos os envios devem possuir um `eventId` estável para
permitir retry sem criar um segundo turno. O próximo `sequence`
deve ser exatamente o último confirmado +1.

## Fluxo conversacional

1. `speech_started` fecha o espaço de fala e coloca o personagem em
   `listening`. É prioritário e não chama o OpenRouter.
2. `turn_chunk` e `turn_end` persistem o texto; o worker chama
   `OBSERVE` e atualiza contexto/postura, **sem publicar speech**.
3. `floor_open` só é aceito com silêncio reconhecido, o mesmo
   `activityEpoch` e captura ligada. O worker espera o contexto de todos
   os eventos anteriores e chama `RESPOND`.
4. `RESPOND` pode decidir `shouldSpeak:false`. Apenas resposta autorizada
   e ainda válida incrementa `speech_seq`.
5. A publicação consulta novamente `active_run_id`, `activity_epoch` e
   estado da captura numa única transação. Respostas atrasadas não aparecem.

A fila `alexios-events-v3` do Vercel desperta o worker, mas **a ordenação
é controlada pelo Neon**, não pelo horário de chegada da queue. Falhas
temporárias repetem o processamento. O banco persiste os eventos recebidos;
a fila é particionada por deployment, portanto mudanças de versão exigem
observar consumidores dos deployments antigos enquanto esgotam trabalhos.

## Avatar

Os oito PNGs versionados já estão em:

`/characters/stand/{crossed-arm,hand-in-pocket}/{listening,speaking,waiting_1,waiting_2}.png`

- `OBSERVE` e `RESPOND` decidem `stance` e `waitingVariant`.
- Início de fala decide `listening` sem consultar a IA.
- Publicação de fala autorizada decide `speaking`, por janela visual
  limitada. Não significa que TTS tenha sido executado.
- Sem fala ou após expirado o tempo visual, exibe `waiting_1` ou
  `waiting_2`.
- Nunca construir a URL diretamente de texto arbitrário retornado pelo modelo.
- Fallback real: `/characters/stand/hand-in-pocket/waiting_1.png`.

## Instalação em produção

1. Verificar CI, testes SQL e imagens em preview com banco Neon separado.
2. Aplicar **somente** a migração `004_v3_events.sql` à branch Neon de
   produção; o esquema é aditivo.
3. Fazer merge da branch web e verificar deployment `READY`.
4. Confirmar `ALEXIOS_WEB_V2_ENABLED=true`, `DATABASE_URL`,
   `OPENROUTER_API_KEY`, `ALEXIOS_AGENT_TOKEN` e
   `ALEXIOS_INSTANCE_HASH_KEY`.
5. Iniciar `python continuous_v3.py` em uma instância de testes.
   Conferir `/sync`, transmissão de turno e `floor_open`.
6. Validar duas pessoas alternando falas, silêncio, interrupção e FIM.
7. Para rollback, parar `continuous_v3.py` e usar `continuous.py`.
   O primeiro envio V2 reativa o processamento legado da instância.

A versão V3 local exige os pesos ONNX e o ambiente instalado conforme
`V3.md` na branch Python. Os testes de CI da web não executam microfone,
Silero, Smart Turn, CAM++ ou Whisper em um Raspberry Pi físico.

## Observabilidade

Neon:
- `alexios_v3_streams.last_accepted_sequence`: eventos persistidos.
- `alexios_v3_streams.last_processed_sequence`: contexto atualizado.
- `alexios_v3_streams.activity_epoch`: última abertura invalidada por nova fala.
- `alexios_v3_events.status`: `pending`, `running`, `processed`,
  `obsolete` ou `failed`.
- `alexios_sessions.context_text`: memória compartilhada de todos os falantes.
- `alexios_sessions.character_stance` e `character_frame`: visual atual.

O modelo atual mantém contexto resumido de até 3.000 caracteres.
Como cada `turn_end` dispara uma avaliação, ambientes de conversação intensa
podem consumir limites ou créditos do OpenRouter. Configurar fallback é
opcional, e nenhuma alteração de provedor é feita automaticamente.
